# 05. 프로토타입 스코프 및 빌드 순서

> v2 (서버권위·RLS 재작성 반영)

## 1. 프로토타입 절단선 (Buildable First Cut)

> 목표: **"꾸미기/먹이 → 배경 반영 → 낚시로 수집"** 의 코어 루프를 한 번 관통.

### 포함 (P0)

- [ ] Supabase: 스키마 + RLS(서버권위 2분류) + seed(어종 5 + 히어로 1, 장식 10, 테마 `deepsea` 기본, 낚시터 `home` 1곳)
- [ ] Auth: 익명 + 이메일 로그인, `handle_new_user()` 트리거로 지갑/프로필 자동 생성
- [ ] Web: 로비 / 꾸미기(슬롯 5) / 상점(카탈로그 + `purchase_item` RPC) / 낚시(1스테이지) / 도감
- [ ] Android: WallpaperService(GL ES 2.0) + 물고기 1~2종 패트롤 + 터치 ripple 파티클
- [ ] **이음새 R1**: 위젯 [먹이] 버튼 → `feed_fish` RPC(서버 권위) → 로컬캐시 optimistic → ContentObserver → 비가시 큐잉 → 홈 복귀 시 드롭 연출
- [ ] 동기화: 웹 저장 → DB(`version++`) → 앱 resume 시 브리지 반영 1회 + SyncWorker 1주기
- [ ] **인증 공유 R8**: `bridge setAuthSession` → 네이티브가 단일 refresh 주체 → 백그라운드 pull 1회 성공 + 토큰 만료 시 재인증 폴백

### 제외 (후속)

- iOS 라이브 배경 동등화 / Live Activity
- 결제(IAP 검증) 실연동 — 가격 사다리·상품ID 카탈로그·`verify-receipt` 경로는 설계만([04 §5](./04-웹앱-백엔드-설계.md))
- 멀티 어항 2번 해금, 시즌 패스, 복잡 낚시·스토리

### P1 (스텁/라벨까지만)

- 소셜 뷰어(`aquarium/[token]`)·하트 선물(`send_heart`/`claim_gifts`): **P1**. 프로토에서는 뷰어 라우트 + RPC 시그니처 스텁까지만(데이터모델/RPC는 [04 §5](./04-웹앱-백엔드-설계.md), 기획서 [04 §6 B5/W5 P1](../기획서/04-서비스-고도화-및-리스크-대응.md))과 정렬.
- 리워드광고(`grant_ad_reward`) 서버 지급, 진행형 알림 액션.

## 2. 빌드 순서 (의존성 기준)

```
B1 스키마/RLS/seed (서버권위 2분류 + themes/fishing_spots/fishing_sessions/synergies)
  → B2 Auth/지갑(handle_new_user 트리거)   → W1 로비+브리지 스텁
  → B3 aquarium+snapshot(slots만 클라 UPDATE, version CAS)  → W2 꾸미기
       → A1 배경(정적+물고기1)  → A2 터치 ripple
       → A3 로컬캐시(ContentObserver)  → A5 인증공유(R8, setAuthSession)
            → A4 위젯먹이+큐잉(R1, feed_fish RPC)  → A6 SyncWorker 백그라운드 pull
  → B 상점 카탈로그(themes/items seed) + purchase_item RPC
       → W3 상점(카탈로그 + 구매 RPC)
  → B4 fishing-resolve(start_fishing → fishing-resolve)  → W4 낚시(optimistic, 실패 폴백)
  → W5 도감
QA: 배터리/게이팅 프로파일 → parity 테스트 → 내부 APK
```

> **A스테이지 순서 주의(서버권위 정합)**: 백그라운드 pull(A6)은 **인증 세션이 선행돼야** 작동하므로, **인증공유(A5)를 SyncWorker 백그라운드 pull(A6) 앞에** 배치한다. 인증 전 단계(A1~A3)에서는 **로컬 캐시 기반 정적 표시**만 하고, 서버 권위 RPC(`feed_fish` 등)는 토큰 확보(A5) 이후 활성화한다.
> **상점 선행(B)**: W3(상점 UI)는 카탈로그 시드 + `purchase_item` RPC(서버 원자 차감/upsert)가 선행돼야 한다. 그래서 W3 앞에 **B: 상점 카탈로그 + `purchase_item` RPC** 단계를 둔다([04 §7 B](./04-웹앱-백엔드-설계.md)).

> 1인 개발 권장 순서: **B(스키마/권위함수) → W(로비/꾸미기) → A(배경·인증·위젯) → 상점(B/W3) → 낚시 → 도감 → iOS**.


## 4.5 마이그레이션 절차 (supabase/migrations)

서버 권위 스키마/함수/RLS/seed는 **선언적 SQL 마이그레이션**으로만 적용한다(수동 콘솔 변경 금지 → 환경 간 드리프트 방지).

### 4.5.1 파일 네이밍 / 순서

- 위치: `supabase/migrations/<UTC_timestamp>_<설명>.sql` (예: `20260601090000_init_schema.sql`).
- 타임스탬프 = **사전식 정렬 = 적용 순서**. 한 마이그레이션 = 한 논리 단위(롤백 단위).
- 권장 분할 순서(의존성 기준):
  1. `..._init_catalog.sql` — `themes`, `fish_species`, `items`, `fishing_spots`, `synergies`(카탈로그 테이블, FK 대상 먼저)
  2. `..._init_user_tables.sql` — `profiles`, `wallets`, `aquariums`, `fish_instances`, `inventory`, `dex_entries`, `share_tokens`, `gifts`, `purchases`, `fishing_sessions`
  3. `..._rls_policies.sql` — RLS 활성화 + SELECT-only 정책(서버권위 2분류, [02 §2](./02-데이터-모델.md))
  4. `..._functions_rpc.sql` — SECURITY DEFINER 함수/RPC([04 §5](./04-웹앱-백엔드-설계.md), [02](./02-데이터-모델.md))
  5. `..._triggers.sql` — `handle_new_user()` + `aqua_pass_until` BEFORE UPDATE 보호 트리거
- 시드는 `supabase/seed/*.sql`로 분리(멱등 upsert), 마이그레이션과 구분.

### 4.5.2 적용 / CI

| 환경 | 적용 방법 |
|------|-----------|
| 로컬 | `supabase db reset`(마이그레이션 전체 재적용 + seed) → `supabase start` |
| dev/prod | `supabase db push`(미적용 마이그레이션만 순차 적용) |
| CI(GitHub Actions) | PR: `supabase db reset` on ephemeral → 마이그레이션 적용 검증 + RLS/RPC 스모크. `main` merge: dev에 `db push`, 수동 승인 후 prod `db push` |

> 함수/RPC 변경은 `create or replace function ...`으로 멱등 작성. 파괴적 변경(컬럼 drop/타입 변경)은 별도 마이그레이션 + 데이터 백필 단계로 분리.

## 5. 환경 설정 / Secrets

| 위치 | 키 |
|------|-----|
| Vercel env | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (anon 한정, RLS 전제) |
| Supabase | DB URL, **service role 키(Edge Fn 환경변수 전용)**, JWT secret |
| Android | `local.properties`/CI Secret(웹 URL, 딥링크 scheme). `.env` 커밋 금지 |
| CI(GitHub Actions) | web lint/test + parity 테스트, android `assembleDebug`, **시크릿 스캔(service role 유출 가드)** |

### 5.1 service role 경계 (서버권위 강제)

- **service role 키는 Edge Function 환경변수에만** 존재한다. 클라이언트 번들(`apps/web`, `apps/android`)·로그·스냅샷·딥링크 어디에도 절대 포함하지 않는다.
- `NEXT_PUBLIC_*` 프리픽스에는 **anon key만** 허용(빌드 시 클라 번들 인라인됨을 전제). service role 키에 `NEXT_PUBLIC_` 부여 금지.
- **유출 가드(CI 필수)**:
  - 시크릿 스캔(gitleaks/trufflehog 등)으로 커밋·번들에서 service role/JWT secret 패턴 검출 시 빌드 실패.
  - 린트 규칙: 클라 코드에서 service role 키 환경변수 참조 금지(allowlist 밖 `process.env` 시크릿 접근 차단).
  - 권위 테이블(`wallets`/`inventory`/`dex_entries`/`fish_instances`/`purchases`/`gifts`) 직접 쓰기 코드 패턴 리뷰 게이트(쓰기는 RPC/Edge Fn 경유만).

## 6. parity 테스트 (web ↔ native 규칙 일치)

서버 권위라도 클라 연출/예측은 **동일 규칙**을 따라야 어긋나지 않는다. `packages/game-spec`에 **공유 테스트벡터**를 두고 양측이 같은 입력으로 같은 출력을 내는지 검증한다.

- **경제 벡터**: 오프라인 적립(`collect_offline` 캡 6h/패스 24h + `coin_rate_bonus`), 하트→코인 환산(100 hearts→1000 coins), 구매 차감(coin/pearl), 스태미나 lazy 재생.
- **FSM 벡터**: 낚시 상태기(`casting→waiting→reeling→resolving→result` + 실패 전이 `waiting timeout→fail`, `reeling 상/하한→fail→result 빈손`), 스킬→보상 매핑(castPerfect 희귀 +10%, timeInZone≥0.9 → 상위 10% size).
- **검증 경로**:
  - web: `packages/game-spec`의 벡터로 단위테스트(`vitest`/`jest`) — CI green 필수.
  - native: 동일 JSON 벡터를 Kotlin 테스트로 로드해 포팅 로직 결과 일치 단언.
- 벡터(기대 입출력)는 **단일 JSON 파일**로 두 런타임이 공유 → 규칙 변경 시 한 곳만 수정, 양측 동시 검증.
