# 04. 웹앱 · 백엔드 설계

> v2 (서버권위·RLS 재작성 반영)

> **대원칙(서버 권위)**: 경제·수집·결제·토큰 테이블은 **클라 직접 쓰기 금지**. 모든 증감은 `SECURITY DEFINER` 함수 또는 service-role Edge Function으로만 수행한다. 클라는 **자기 행 SELECT만** 가능하다. RLS 정의는 [02 §2](./02-데이터-모델.md#2-rls-정책-서버-권위)를 단일 진실원으로 따른다.

## 1. Next.js (App Router) 구조

    decorate/page.tsx       # 슬롯 배치 → DB upsert
    shop/page.tsx           # 카탈로그 + 구매 RPC + 데일리 슬롯
    fishing/page.tsx        # Pixi 미니게임
    dex/page.tsx            # 도감(수집 메타)
    aquarium/[token]/page.tsx  # ★공유 어항 뷰어(불투명 토큰, read-only) — P1
  components/
  lib/
    supabase/               # 클라이언트, 타입
    bridge/                 # postMessage/AquaDesk 브리지 래퍼
  public/sprites/

packages/
  game-spec/                # ★순수 TS(I/O 없음): economy, fsm, snapshot 변환 (네이티브와 규칙 공유)

- **`lib/game` 위치 단일화 → `packages/game-spec`**: 경제 계산·FSM 규칙·DB row→`AquariumSnapshot` 변환을 담는 **I/O 없는 순수 TS 패키지**. `apps/web`가 import한다. 04/05 모두 이 경로(`packages/game-spec`)로 통일한다([05 §4](./05-프로토타입-스코프-및-순서.md#4-레포-구조-monorepo-권장)).
  - 테스트 용이 + 네이티브 포팅 스펙의 단일 출처. 공유 테스트벡터(경제/FSM)는 [05 §6](./05-프로토타입-스코프-및-순서.md)의 parity 테스트에서 web 단위테스트 + native 동일벡터 검증에 사용한다.
- 네이티브 WebView UA 감지 → safe-area CSS + 브리지 활성화.

## 2. Supabase 연동 / 인증

- `@supabase/supabase-js`, `anon key` + RLS. **service role 키는 Edge Function 환경변수에만** 존재하며 클라 번들/로그에 절대 유출 금지([05 §5](./05-프로토타입-스코프-및-순서.md#5-환경-설정--secrets)의 시크릿 스캔/린트 가드 참조).
- env: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

### 2.1 세션·인증 모델 (R8 — 네이티브 단일 refresh 주체)

- 로그인(이메일/익명) 성공 시 → `AquaDesk.setAuthSession(refreshToken)`로 네이티브에 세션 공유([03 §6](./03-네이티브-안드로이드-설계.md), [02 §5](./02-데이터-모델.md#5-브리지--딥링크-api)).
- **웹 독립 refresh 금지**: 웹앱은 resume 시 브리지 `getAuthSession()`으로 **네이티브 세션을 읽어 재사용**한다. 토큰 refresh의 단일 주체는 네이티브다. `invalid refresh` 시 재인증 유도 폴백.
- **익명 → 이메일 병합(계정 승격)**: Supabase `linkIdentity`로 익명 계정을 이메일 계정으로 승격하며 **익명 데이터(어항·도감·지갑)를 보존**한다([01](./01-시스템-아키텍처.md) 동시성/계정 참조).

## 3. 낚시 미니게임 (PixiJS) — 상태 머신

> 순수 FSM 규칙은 `packages/game-spec`에 위치하며 web/native 동일 벡터로 검증된다.

```
       casting ──tap(Perfect?)──▶ waiting ──bite──▶ reeling ──success──▶ resolving ──▶ result
          │                          │                │                                  ▲
          │ 게이지 타이밍            │ "!" 1.0s 내 tap │ greenzone 3s 유지                │
          │                          │                │                                  │
          └ (cast fail)──────────────┴─(timeout)──────┴─(상/하한 이탈)──▶ fail ──────────┘
                                                                          (빈손 result)
```

```typescript
type FishingState =
  | 'casting'
  | 'waiting'
  | 'reeling'
  | 'resolving'
  | 'result'
  | 'fail';     // ★실패 전이(빈손) → result로 합류

interface FishingSkill {
  castPerfect: boolean;   // 희귀종 확률 +10%
  timeInZone: number;     // 0..1, ≥0.9 → Perfect Catch(상위 10% 크기)
}
```

### 3.1 ★실패 전이 (신규)

- `waiting`에서 **입질 후 1.0초 내 미탭 → timeout → fail**.
- `reeling`에서 찌가 **그린존 상한/하한을 이탈 → fail**.
- `fail` 상태는 빈손(보상 없음) `result`로 합류한다. 즉 **클라가 임의로 '성공'을 확정하지 않는다** — 성공으로 진입하는 경우에만 `resolving`을 거친다.

## 4. ★낚시 Optimistic UI + 서버 정합

낚시는 두 단계로 멱등 처리한다: `start_fishing`으로 **세션을 선점**(스태미나 게이트)하고, `fishing-resolve`로 **무엇을 잡았는지** 결정한다. 임시지급 멱등키는 `fishing_sessions.id`다([02 §1](./02-데이터-모델.md#1-postgres-스키마-supabase)).

```
진입 시:
  0) session_id = await start_fishing(spotId)   [스태미나-1, 부족 시 거부 → 진입 차단]

reeling 성공:
  1) 즉시 성공 연출(들어올리기) 1.5~2s 구동                 [클라가 '성공' 확정, 서버는 뒤집지 않음]
  2) await fishing-resolve(session_id, skill)              [서버가 '무엇'만 결정, 보상 쓰기 전부 서버]
  3) 응답 도착 → result 팝업(종/크기 sizePct)
  4) fish_instances/dex/wallets는 서버가 갱신 → 클라는 재조회(SELECT)만

응답 지연(★'연출종료==응답도착' 가정 제거):
  · 연출 종료 후 응답 미도착이면 스피너 표시(대기)
  · 일정 타임아웃 초과 시 session_id로 재동기화(fishing-resolve 재호출, 멱등)
    └ 이미 consumed면 서버가 기존 reward를 그대로 반환 → 결과 복원
  · 통신 단절로 잡은 물고기가 증발하지 않음(서버 권위 + 멱등키=session_id)

실패(낚시 FSM fail):
  · resolve를 호출하지 않음(빈손). start_fishing으로 차감한 스태미나는 반환하지 않음(설계 다이얼).
```

> **불변 규칙**: 서버는 **"무엇을 잡았나"만** 결정하고 **"잡았나/못 잡았나"는 절대 뒤집지 않는다**(성공 연출 후 사실상 실패 금지). 이전 v1의 "연출종료 == 응답도착" 가정은 **제거**되었으며, 지연은 스피너 + `fishing_sessions` 기반 멱등 재동기화로 흡수한다.

## 5. 서버 권위 함수/RPC (단일 진실원)

모든 상태변경은 `SECURITY DEFINER` RPC 또는 **service-role Edge Function**으로만 수행한다. 클라는 자기 행 SELECT만 한다. 함수 본문(SQL)·트리거는 [02](./02-데이터-모델.md)와 정확히 일치한다.

| 함수/RPC | 종류 | 입력 | 책임 | 멱등/동시성 |
|----------|------|------|------|-------------|
| `start_fishing` | RPC (SEC DEF) | `spot_id` | lazy 스태미나 재생(`stamina_updated_at` 기준 +1/Nmin, cap) → `stamina-1` → `fishing_sessions` insert → `session_id` 반환. 부족 시 거부 | 세션 row가 멱등/중복지급 방지 키 |
| `fishing-resolve` | Edge (service role) | `session_id`, `skill` | session 미consumed 검증 → spot `species_pool`+`rarity_weights`+seed로 **종 결정**, skill로 `size_pct`·희귀확률 보정 → `fish_instances` insert + `dex_entries` upsert + `consumed=true` + reward 연결 | **멱등**: 이미 consumed면 기존 reward 반환 |
| `feed_fish` | RPC (SEC DEF) | `aquarium_id` | `hunger`/관련 상태 갱신 + `version` CAS. 위젯/알림/앱 모두 이 RPC 호출(토큰 필요) | `version` CAS |
| `clean_aquarium` | RPC (SEC DEF) | `aquarium_id` | `water_quality` 갱신 + `version` CAS. 위젯/알림/앱 모두 이 RPC 호출(토큰 필요) | `version` CAS |
| `collect_offline` | RPC (SEC DEF) | `aquarium_id` | `last_collected_at`·`aqua_pass_until` 기준 코인 적립(캡 **6h**, 패스 **24h**) + `last_collected_at` 갱신 + `coin_rate_bonus` 반영 | `version` CAS |
| `purchase_item` | RPC (SEC DEF) | `item_id` | 가격(`price_coin`/`price_pearl`) **원자 차감** + `inventory` upsert | `version`/조건부 차감 CAS |
| `daily-shop-roll` | Edge | – | `date + user_id` 시드로 일일 **6슬롯** 결정(클라 조작 불가) | date+user 결정적 시드 |
| `verify-receipt` | Edge (service role) | `platform`, `receipt` | 영수증 검증 → `purchases.receipt` **UNIQUE로 멱등** → `pearls`/items **원자 지급** + `verified=true` | `unique(platform, receipt)` |
| `issue_share_token` | RPC (SEC DEF) | `aquarium_idx` | **16자+ 불투명 토큰** 생성·저장, **토큰만 반환**(URL은 토큰만 노출) | – |
| `get_shared_aquarium` | RPC (SEC DEF) | `token` | **만료 검사 후 read-only 스냅샷** 반환. `user_id`는 **절대 미반환** | – |
| `send_heart` | RPC (SEC DEF) | `to_token` | 토큰→대상 user 해석 → 자기선물 차단 → 레이트리밋(대상별 일 5회) → `gifts` insert | 레이트리밋 |
| `claim_gifts` | RPC (SEC DEF) | – | 미수령 `gifts` → `wallets.hearts` 적립 + `claimed=true`. hearts 임계(**100**) 도달 시 claim 내에서 **코인 환산(100 hearts→1000 coins)** | `claimed` 플래그 |
| `grant_ad_reward` | Edge | `kind` | 리워드광고 보상(`stamina+1` / offline `x2` / `shop refresh`) **서버 지급**, **1일 횟수 제한**(광고 SSV/검증) | 일 횟수 제한 + SSV |
| `set_aquarium_theme` | RPC (SEC DEF) | `aquarium_id uuid`, `theme_id text` | 테마 변경 시 **소유검증**(클라는 `theme_id` 직접 UPDATE 금지). 보호 컬럼이므로 쓰기 전 `app.authority_write` 플래그 설정([02 §3.2](./02-데이터-모델.md)) | 소유검증 |

> **공유 보안(R6)**: 공유 어항 뷰어는 `aquarium/[token]`로 진입 → 서버(`get_shared_aquarium`)가 토큰→user 매핑을 **내부 처리**하고 **read-only 스냅샷만** 반환한다. `share_tokens`는 클라 직접 SELECT/INSERT가 모두 금지(정책 없음=거부)이며 **`issue_share_token`/`get_shared_aquarium` RPC 전용**이다. `user_id`는 클라에 절대 노출하지 않는다.

> **동시성(version CAS)**: 모든 상태변경 RPC는 `UPDATE ... WHERE id = ? AND version = ?` 형태의 CAS로 수행한다. **불일치 시 `conflict` 반환** → 클라가 refresh 후 재시도한다. last-write-wins는 이 정책으로 대체된다([01](./01-시스템-아키텍처.md) lost-update 방지).

### 5.1 리워드 광고 설계 (`grant_ad_reward`)

- **SDK 통합 지점**: 웹앱(`apps/web`)이 리워드 비디오 SDK를 로드·표시한다. **클라는 보상을 직접 지급하지 않는다.**
- **서버 지급 흐름**: SDK 보상 콜백 → SSV(Server-Side Verification) 또는 토큰 → `grant_ad_reward(kind)` Edge Function이 검증 후 **서버가 보상을 지급**한다.
- **보상 종류(`kind`)**: `stamina`(+1) / `offline_x2`(오프라인 적립 2배) / `shop_refresh`(상점 무료 리프레시).
- **남용 방지**: `kind`별 **1일 횟수 제한** + 광고 SSV/검증으로 위조 콜백 차단.

### 5.2 데일리 상점 (`daily-shop-roll`)

- `date + user_id` 시드로 **6슬롯**을 결정적으로 생성(클라 조작 불가). 구매는 `purchase_item` RPC로 처리한다.

## 6. IAP 상품 카탈로그 (가격 사다리 → 상품ID)

> 기준: **1 진주 ≈ 120원**([기획서 04 §3.4](../기획서/04-서비스-고도화-및-리스크-대응.md#34-iap-가격-사다리-보정--진주-팩--스타터팩--상품)). 결제는 **`verify-receipt`** Edge Function이 영수증을 검증하고 `purchases.receipt` UNIQUE로 멱등 지급한다. 스토어 등록은 아래 `product_id` 카탈로그를 단일 진실원으로 한다.

### (A) 진주 팩 — 보너스 체증형

| `product_id` | 가격(원) | 진주 | 보너스 |
|---|---|---|---|
| `pearl_pack_10` | 1,200 | 10 | – |
| `pearl_pack_50` | 5,500 | 50 | +9% |
| `pearl_pack_115` | 12,000 | 115 | +15% |
| `pearl_pack_260` | 25,000 | 260 | +30% |
| `pearl_pack_540` | 49,000 | 540 | +35% (고래 앵커) |

### (B) 스타터팩 (첫구매 1회)

| `product_id` | 가격(원) | 구성 |
|---|---|---|
| `starter_pack` | 2,900 | 진주 30 + 한정 장식 + 코인 보너스 |

### (C) 상품 — 테마/히어로 (진주 소비, IAP 직접결제 아님 → `purchase_item` 경로)

| `product_id` | 진주 | 비고 |
|---|---|---|
| 테마 스킨(핵심·반복) | **50~80** | 충동구매 대역. `items.type='theme'`, `themes.is_premium=true` |
| 한정/번들 테마 | 120~150 | 18,000원+는 한정/번들에 배치 |
| `hero_fish_*`(신화 히어로 어종, 확정 분양) | **400** | 고래 앵커. 가챠 아님(확정) = Route A 정합 |

- (A)/(B)는 스토어 IAP(진주/스타터 구매) → `verify-receipt`로 지급.
- (C) 테마·히어로는 **인게임 재화(진주) 소비** → `purchase_item` RPC로 차감/지급(소유검증·원자 차감).

## 7. 구축 단계 (웹/백엔드)

> 빌드그래프 전체·마이그레이션 절차는 [05 §2](./05-프로토타입-스코프-및-순서.md#2-빌드-순서-의존성-기준)를 단일 진실원으로 한다.

| 단계 | 산출물 |
|------|--------|
| B1 | 스키마 + RLS(2분류) + seed(`fish_species`/`items`/`themes`/`fishing_spots`/`synergies`) |
| B2 | Auth + `handle_new_user` trigger(profile/wallet 자동 생성) |
| B3 | aquarium CRUD(slots만 클라 UPDATE) + `version` CAS + snapshot 변환 |
| **B** | **상점 카탈로그 + `purchase_item` RPC** (★W3 상점 선행) |
| B4 | `start_fishing` + `fishing-resolve`(멱등) + `fish_instances` + `dex_entries` |
| B5 | `issue_share_token` + `get_shared_aquarium` + 공유 어항 뷰어 — **P1** |
| W1 | Auth + lobby shell + 브리지 스텁 |
| W2 | Decorate(슬롯 → upsert) |
| W3 | Shop(카탈로그 + `purchase_item` RPC + `daily-shop-roll`) — 선행 **B** 필요 |
| W4 | Fishing(Pixi 1스테이지 + optimistic + 실패전이 + 지연 재동기화) |
| W5 | Dex + **Social viewer — P1** |

> **소셜 뷰어 = P1**: B5/W5의 공유 어항 뷰어·하트는 P1 범위이며, [05 §1](./05-프로토타입-스코프-및-순서.md#1-프로토타입-절단선-buildable-first-cut)의 "소셜은 스텁까지만(P1)"과 정렬한다.
